1. Session Browser Command
Add a `sessions` positional subcommand to the harness CLI so saved runs can be inspected and cleaned up without remembering ids. Context: cli.ts parses arguments with a table-driven parser and a `COMMANDS` array (`run`/`doctor`/`setup`); a leading positional that names a recognized command is stripped before the prompt is assembled, and `doctor`/`setup` each dispatch to their own module and return without starting a run. session.ts already exports `listSessions`, `loadSession`, and `newSessionId`, and `--save-session`/`--resume <id>` already write and read those records. Scope: register `sessions` in `COMMANDS`, add it to `USAGE`, and handle it in `main()` before the prompt/run path, mirroring the `doctor` branch. Ship `mhh sessions` (one line per saved session: id, model, turn count, and a truncated first user message), `mhh sessions show <id>` (the full saved record via `loadSession`), `mhh sessions rm <id>` (delete, prompting unless `--yes`), and `--json` output for list. Add a `removeSession(id)` helper to session.ts rather than deleting files from cli.ts. Expected behavior and edge cases: an empty or missing state directory prints a friendly 'no saved sessions' line and exits 0; an unknown id prints an error to stderr, lists the known ids the way the existing `--resume` failure path does, and exits 1; the literal word `sessions` must never leak into a task prompt; `--resume` and `--save-session` behavior must be unchanged; deleting a session must not touch that run's snapshot directory. Validation: run a task with `--save-session`, then verify list, show, `--json` (must parse with `JSON.parse`), and `rm`; re-run each subcommand with the state directory absent and confirm the friendly paths and exit codes.

2. Approval Policy Memory
Stop re-prompting for the same mutating tool call twice in a run. Context: the plaintext gate in cli.ts (`onApproval`) renders the approval card, checks `mayAutoApprove(request.risk)` from risk.ts, honors `--yes`, declines when stdin is not a TTY, and otherwise asks `  proceed? [y/N]` through the renderer; `--auto-approve-safe` only skips calls classified `safe`. Scope: extend the gate's question to accept `y` (once), `a` (always for this session), `p` (persist a rule for this workspace), and `n`. Session rules live in memory for the process; persisted rules go in the harness state directory alongside sessions and snapshots, keyed by workspace, as JSON. A rule matches on tool name plus a normalized target — the command string for `bash`/`run_command`, the file path for write/edit tools — and must be recorded as an exact match, not a prefix, unless the user is shown the widened pattern. Expected behavior and edge cases: rules never override a decline and never apply when `--yes` is absent on a non-TTY stdin path, which must keep its current decline message; when no risk classifier is configured, still allow session rules but require explicit confirmation wording for `bash` before persisting; a rule recorded for a call that risk.ts later classifies `caution` or `dangerous` must re-prompt and say why; a corrupt or unreadable rules file logs one warning to stderr and behaves as if no rules exist; every auto-approval is printed with the rule that matched, as the `safe` path already does. Validation: with a fake classifier, confirm `a` suppresses the second identical call and a third differing call still prompts, restart the process to confirm only `p` rules survive, corrupt the rules file and confirm the run continues, and confirm `--yes` and `--auto-approve-safe` are unaffected.

3. Conversation Context Compaction
Give the harness mid-run context compaction, so a long task does not die on a context limit. Today summarize.ts only shrinks oversized tool results (`summarizeToolOutput`, `DEFAULT_SUMMARIZE_THRESHOLD`), while index.ts keeps the full `messages` array for the whole run. Add an opt-in `--compact` / `--compact-threshold <n>` (and `--no-compact`) plus `compactThreshold?: number` on `HarnessOptions`; when the accumulated message content exceeds the threshold, replace the oldest completed turns with a digest produced by the same client the run already uses — reuse the `digestFrom(runtime)` helper pattern in index.ts so summarize.ts stays provider-neutral. Correctness rules that must hold: never touch the system message, never split an assistant message carrying tool calls from its matching tool results (drop or keep them as a unit, or the next model call is malformed), always keep the most recent turns verbatim, and never compact on the resumed path in a way that rewrites what `saveSession` later persists without noting it. Announce each compaction on stderr (for example `[harness] compacted 6 turns into 1`) so a reader knows history was rewritten. Edge cases: threshold below a single turn's size, compaction while a subagent delegation from subagents.ts is in flight, and compaction on a run whose messages came from `initialMessages` (--resume). Validate with a scripted fake client that asserts message pairing stays valid after several compactions and that the digest replaces, rather than duplicates, the old turns.

4. Machine Readable Run Events
Add a `--json-events` flag that turns a run into NDJSON on stdout for CI and log tooling. Leave the existing `--json` untouched, since it is scoped to `doctor`. In `cli.ts`, register the flag as bool, force the plaintext path (like `--plain`) so transcript text never interleaves with records, and keep diagnostics on stderr. Emit one line per: run start (task, model, session id, workspace, schema version), text delta, `tool` event (name, arguments, outcome, durationMs, truncated flag), approval decision (approved, auto-approved, or declined, with risk level), turn (turns, tokens), and done (summary totals). Reuse what `runPlaintext` already computes — `lastEventAt`, `outcomeFromText`, `autoApproved`. Edge cases: multi-line tool bodies must be escaped, never split across lines; `--summarize-tools` results must be marked truncated so consumers know the body is not raw; `--tui --json-events` must fail loudly rather than emit nothing; a declined approval still emits a record. Validate by piping a stub-runtime run through a JSON-lines parser in a test, asserting every line parses and event order matches the plaintext transcript.

5. Repeated Read Deduplication
Stop the model paying twice for the same unchanged file. Add a per-run read cache to the tool execution path (`tools.ts` plus the executor wired in `index.ts`): key on the resolved real path so symlinks collapse, and store byte length, mtime, and the returned body. When the same path is read again with unchanged size and mtime, return a short envelope — the path plus 'unchanged since turn N' — instead of the full body, noting which turn supplied the original read. Invalidate the whole cache after any mutating call (`isMutatingToolCall`) and revalidate per path on every read so a file changed by `bash` is never served stale. Keep the cache in memory only, scoped to one run, never written to the session or snapshot directory. Edge cases: concurrent read-only calls in one batch (dedupe against in-flight reads rather than racing them); a body already summarized by `summarizeToolOutput` must keep its truncated marker; a file deleted between reads must fall through to the normal error. Validate with unit tests that bump mtime between reads and assert the post-mutation read is fresh, plus an integration run whose transcript shows one full body and one 'unchanged' line.
